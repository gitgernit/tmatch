## 0. Архитектура

Используются два подхода к проектированию:

1. **Clean Architecture**
2. **Domain Driven Design**

Оба ставят предметную область (бизнес-логику, домен) в центр: она разрабатывается изолированно, тестируемо и расширяемо. Зависимости направлены внутрь: домен не зависит от способа хранения данных, от HTTP или конкретных API.

### Clean Architecture

Система разделена на слои по ответственности. Внутренние слои не зависят от внешних.

1. **Доменный слой** — сущности, value objects, инварианты и базовое поведение данных предметной области.
2. **Слой приложения** — сценарии использования (use cases): оркестрация доменной логики и обращение к абстракциям хранилищ и внешних сервисов.
3. **Слой презентации** — точки входа: HTTP API, роуты, DTO, вызов сценариев из слоя приложения.
4. **Инфраструктурный слой** — технические реализации: БД, вызов внешних API, очереди, логирование.

Зависимости идут от внешних слоёв к внутренним. Домен и слой приложения не зависят от SQL, HTTP или конкретных провайдеров. Это даёт возможность подменять реализации (например, mock-хранилище в тестах) и расширять систему без переписывания ядра.

**Инверсия зависимостей:** слой приложения объявляет интерфейсы (например, data gateway, unit of work), а реализации подставляются из инфраструктуры во время выполнения.

### Domain Driven Design

Используется базовая часть методологии — термины и принципы моделирования предметной области:

- **Агрегат** — группа объектов, связанных по смыслу; изменения проходят через корень агрегата.
- **Агрегатный корень** — объект, через который обращаются к агрегату.
- **Сущность (entity)** — объект с устойчивым идентификатором и жизненным циклом.
- **Объект-значение (value object)** — объект, определяемый только набором полей, без собственного идентификатора и жизненного цикла.

Доменный слой опирается на эти понятия; слой приложения оперирует сущностями и value objects, а не «сырыми» структурами БД или API.

## 1. Карта репозитория

### Точка входа

- **Запуск:** `uv run api` (скрипт в `pyproject.toml`: `api = "app.presentation.api.bootstrap.main:sync_entrypoint"`).
- **Инициализация приложения:** `src/app/presentation/api/bootstrap/main.py` — создание приложения, регистрация роутов, DI, persistence, запуск сервера.

### Структура по слоям

| Путь | Назначение |
|------|------------|
| `src/app/domain/` | Доменный слой: сущности, value objects, инварианты |
| `src/app/application/` | Слой приложения: интеракторы (сценарии), абстракции (data gateways, провайдеры) |
| `src/app/presentation/` | Слой презентации: HTTP API, роутеры, DTO, bootstrap |
| `src/app/infra/` | Инфраструктура: БД (SQLAlchemy), вызов ML, WebSocket, логирование, конфиг |
| `tests/` | Тесты (unit, integration, e2e) |
| `docs/` | Документация |

Запрос проходит по цепочке: роут (presentation) → DTO → интерактор (application) → data gateway / unit of work (infra) → доменные типы (domain). Бизнес-логика сосредоточена в application и domain; presentation и infra остаются тонкими адаптерами.

## 2. Интеграции

- **Чаты:** доставка сообщений по HTTP (поллинг списка чатов и сообщений) и по WebSocket (real-time при открытом соединении).
- **Пуш-уведомления:** FCM (Firebase Cloud Messaging); регистрация устройств, отправка по событиям (например, новое сообщение в чате).
- **Рекомендации:** вызов внешнего ML-сервиса по HTTP; в тестах подставляется mock-провайдер.

---

## 3. Тестирование

- **Unit-тесты** — доменные правила и изолированная логика.
- **Интеграционные тесты** — сценарии с реальной БД и контейнером приложения (регистрация, рекомендации, лайки, мэтчи, чаты, таргетинг и т.д.).
- **E2E** — проверка API по HTTP: валидация входных данных (400/422), авторизация (401), успешные ответы.

**Запуск:** `make test` или `uv run pytest`. Линтинг и тесты перед коммитом: `make check`.

**Покрытие:** на текущий момент — порядка 76% (line coverage); отчёт: `uv run pytest --cov` или `make test-cov`.
